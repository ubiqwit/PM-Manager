# Cloudflare Workers + D1 + Access, with money writes as D1 batches

The MVP runs as one TypeScript Cloudflare Worker at `pm.shaunmalhotra.com`. Its data lives in a D1 (SQLite) database, and Cloudflare Access lets in only the Manager. It was the only option that costs $0/mo, works from any device including a phone, and needs no login code or servers to look after. We accepted that the data is stored outside Canada: the law doesn't require Canadian storage (PIPEDA allows it if people are told), and D1 has no Canadian location. See [Choose platform and stack](https://github.com/ubiqwit/PM-Manager/issues/10).

## Considered Options

- **Portable web app + SQLite + Litestream on Fly.io Toronto**: data stays in Canada and the app is easy to move to another host. Rejected because it costs about $2–4/mo (Fly has no free tier) and we would have to build the login or put Access in front.
- **Tauri desktop app with SQLCipher**: the data never leaves the Manager's machine. Rejected because it runs on one device only, we would be responsible for backups, and we would have to sign installers and ship updates.
- **Supabase / Neon**: their free plans pause or keep almost no restore history. The first plan that is safe to use costs $25/mo.
- **GitHub Pages at `shaunmalhotra.com/pm`**: Pages only serves static files, so it can't keep private data or check a login.

## Consequences

- **D1 has no interactive transactions** (Drizzle's `transaction()` fails on D1). Every money write is therefore built up front and sent as a single `db.batch()`, which either succeeds completely or rolls back:
  - IDs are generated by the app.
  - Rules are enforced by the database schema (CHECK, FK and UNIQUE constraints).
  - An idempotency key stops a payment being saved twice.

  The batch is wrapped in a unit-of-work function inside the one repository module. Don't "fix" this into transactions. Because the seam hides the batch, a later move to a server running SQLite or Postgres would map it onto an ordinary transaction.
- Tests run against real D1 inside workerd, not better-sqlite3, because better-sqlite3 has real transactions and would pass code that fails on D1.
- The 10 ms CPU limit per request on the free plan rules out generating PDFs in the Worker. Reports are print-styled HTML pages that the Manager saves as PDF from the browser.
- The domain's DNS moves to Cloudflare nameservers, because Access and Workers Custom Domains need a full zone on the Free plan. The GitHub Pages records stay DNS-only (not proxied).
- Backups: D1 keeps 7 days of restore history on the free plan. To reach further back:
  - a nightly export of every table goes to R2 and is kept for 35 days;
  - year-end snapshots are kept indefinitely;
  - each year the Manager downloads a year-end pack and keeps it somewhere other than Cloudflare.
